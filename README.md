### Структура репозитория

Для того, чтобы не плодить 67 репозиторией для каждой рабораторной работы было принято
решение всё делать в рамках одного решения/репозитория. Каждая директория - есть папка
решения, имя директории зависит от самой темы лабораторной работы. Внутри этой папки
обычно находится 2 проекта - первый с бизнес логикой, второй с интерфейсом. Имя первого
чаще всего `[Название ЛР].BuisnessLogic`, второго - зависит от фреймворка, на котором
писан интерфейс, например `[Название ЛР].WPF`.

В стороне стоит папка `Tests`, внутри неё находятся проекты с тестами. В качестве
фреймворка тестирования используется `xUnit.3`. Имя проекта в таком случае:
`[Название ЛР].Tests`.

Я лично слежу за соблюдением ***__naming convention__*** в названиях проекта, папках, переменных,
классах и функциях/методах. Прошу заметить, что почти нигде не используется `snake_case`, почти
везде используется `PascalCase` (в названиях **проектов**, **папок решения**, **классов**, **методов**/**функций**).
`UPPER_CASE` используется в константах, а `camelCase` используется в **переменных** и **аргументах**.
К отступу я не сильно придираюсь, есть предпочтение в отступе размером в 2 пробела (4 пробела кажутся
громоздкими). `snake_case` имеет смысл использовать в приватных полях, при этом они начинаются с `_`.
___Подробнее [здесь](./.editorconfig)___.

### Инъекция зависимостей

Пожалуйста, используете в фронтенде инъекцию зависимостей, чтобы не создавать непонятное дерево, что
состоит из ста функций и классов, в которые вкладывается объект.

Зависимости пишем в `App.(a)xaml.cs` внутри `_configureServices`, эталон
здесь: [`Contracts.Avalonia`](./Contracts/Contracts.Avalonia/App.axaml.cs).

> [!NOTE]
> Эталон не значит лучший, эталон значит пример

### Развёртка

Выполните этот код в своей командной оболочке:
```shell
# Склонировать репозиторий
git clone git@github.com:tstu-artemos-projects/TheoreticalInformaticsLabs.git
# Перейти в директорию проекта
cd TheoreticalInformaticsLabs
# Собрать и запустить проект
dotnet run
```
